# RAWDesk — Reconstructed Product Specification

Reconstructed from repository evidence: source, tests, documentation, and QA
artifacts. Documentation claims were verified against implementation rather than
accepted; where they diverge, the divergence is recorded.

> **Naming.** The deliverable was requested as "RawDock". The product in this
> repository is **RAWDesk** — `Package.swift:5`, `project.yml:1`, bundle id
> `local.rawdesk.app`, and every document and screenshot. No artifact anywhere
> uses "RawDock". This spec assumes they refer to the same product. If they do
> not, this is the first thing to resolve.

---

## 1. What RAWDesk is

> "RAWDesk is a macOS-native, local-first photo organizer and non-destructive RAW
> editor." — `README.md:3-4`

**This claim is supported by the implementation.** All four load-bearing parts
were verified:

| Claim | Verification |
|---|---|
| macOS-native | SwiftUI/AppKit, zero third-party dependencies (`Package.swift`) |
| local-first | No networking code anywhere; no sync, no accounts, no telemetry |
| organizer | 15-table SQLite catalog, collections, keywords, stacks, people, map |
| non-destructive | **Only one image-writing call exists in the codebase**, and it targets a user-chosen export path (`ImageExporter.swift:59`) |

### The workflow it targets

Evidence points to a **single-photographer, single-machine, post-shoot
review-and-develop loop**:

```
card / folder  →  verified import  →  cull & rate  →  develop  →  export JPEG/PNG
```

Supporting evidence: verified-hash import with a dedicated watched-folder ingest
for camera downloads (`AutoImportService`); Assisted Culling with focus/eye/
exposure/misfire signals (`AssistedCullingAnalyzer`); Compare, Survey, and
Reference review layouts (`WorkspaceMode.swift:196-581`); pick/reject/rating/
color-label state (`PhotoUserState`); a full develop stack; JPEG/PNG export only.

### What it is not

- **Not a cloud or multi-device product.** No networking, sync, or accounts.
- **Not a shared-catalog or collaboration tool.** Single local SQLite file.
- **Not a viewer.** The develop stack and catalog far exceed viewer scope.
- **Not an asset-management system for teams.** No roles, no publication.
- **Not a Lightroom replacement**, and does not claim to be —
  `README.md:11-14` states this explicitly and devotes a long section to gaps.
- **Not a delivery/print tool.** No TIFF, no 16-bit, no print, no plugins.

### Managed vs. referenced originals

RAWDesk supports **both**, chosen per import (`PhotoImportModels.swift:3-37`):

| Mode | Behavior |
|---|---|
| `addInPlace` ("Add") | Reference in place. Nothing is copied or moved. |
| `copyToFolder` ("Copy") | Verified copy into a destination folder. Source untouched. |
| `moveToFolder` ("Move") | Verified copy, catalog commit, then **permanent deletion** of the source. |

Critically, **"managed" does not mean an opaque library container.** Even
copied/moved originals remain ordinary files in an ordinary user-chosen folder.
The catalog only ever *references* paths. There is no bundle, no package, no
proprietary store. A user can delete the catalog and still have every photograph.

## 2. Supported formats

`Models/FileFormat.swift` — non-RAW: **JPEG, PNG, HEIC, TIFF**. RAW: **Sony ARW,
Canon CR2, Canon CR3, Adobe DNG, Nikon NEF, Fuji RAF, Panasonic RW2, Olympus
ORF**, plus an `unknownRaw` bucket.

**This list must be read carefully.** `FileFormat` is assigned purely from the
**file extension** (`FileTypeDetector`), and RAWDesk **implements no demosaic of
its own** — every RAW is handed to Apple's `CIRAWFilter`
(`RAWImageLoader.swift:193`). The enum therefore describes which extensions are
*recognized and labeled*, not which cameras are verified to decode correctly.

`README.md` is honest about this: *"Full-fidelity RAW support remains bounded by
the installed macOS RAW decoder; there is no bundled third-party camera SDK."*

**Actually verified:** only **Sony ARW** end to end, against a real file
(`ETH01641.ARW`) in a release-gated QA pass
(`Releases/RAWDesk-v0.1-Sony-ARW-Verified-2026-07-27/Sony-ARW-QA/`). Canon CR2 has
a fixture (`testraw/IMG_0002.CR2`) but no verified pipeline evidence. The other
six RAW formats have **no verification evidence of any kind**.

**Export formats: JPEG and PNG only** (`ImageExporter.swift:8-25`). No TIFF, no
16-bit, no wide-gamut output.

## 3. Data model

`PhotoAsset` is the central entity and *is* a file — there is no separate
photo/file abstraction and no master/version hierarchy at the asset level. All
user-authored data (rating, pick, favorite, color label, keywords, note, location
override, adjustments, named edit versions) lives in `PhotoUserState`, serialized
to JSON.

Identity (`PhotoAsset.id`) is generated by `PhotoLibraryScanner.stableID`
(`:189-200`): the OS `fileResourceIdentifier` when available, otherwise
`path|size|mtime`. **This is the most fragile design decision in the product** —
see `RAWDOCK_ARCHITECTURE.md` §3.1 and `RAWDOCK_DATA_SAFETY.md` §6.4.

## 4. Feature specification

### 4.1 Import — the strongest subsystem

Preflight (discovery, hashing, duplicate detection) precedes execution. Every
copy is written to a temp file, **SHA-256 verified**, then atomically moved
(`PhotoImportService.swift:1071-1093`). Destination collisions never overwrite —
up to 10,000 numbered suffixes, with exact-hash reuse
(`:1023-1069`). Move-mode deletion re-verifies **both** source and destination
hashes immediately before removal (`:878-885`).

Also supported: sibling XMP companionship, folder organization (single / capture
date / custom template), filename templating with validated tokens, import-time
keywords and develop presets.

**Auto Import** (`AutoImportService`) watches a folder, waits for byte-stable
writes, ingests, and **permanently deletes the watched-folder source**. It is
disabled by default and the UI discloses the deletion clearly. See §6.

### 4.2 Non-destructive editing — confirmed, structurally enforced

46 adjustment parameters (`PhotoAdjustments.swift`), **all consumed by
`PhotoProcessor`** (verified field by field). Adjustments are stored in
`PhotoUserState` and re-applied at render; the source is never rewritten. Named
edit versions are supported (`EditVersion.swift`), along with presets, multi-photo
sync (`PhotoAdjustmentSync.swift`), and undo/redo.

Local adjustments include brush, radial, linear, color, luminance, sky, subject,
object, and embedded-depth masks, backed by real Vision requests
(`SubjectMaskGenerator.swift:160` uses `VNGenerateForegroundInstanceMaskRequest`).

### 4.3 Color management — real for display, thin for export

**Display/proofing is genuinely color-managed.** `SoftProofProfileCatalog` uses
ColorSync to enumerate installed ICC profiles (`:71`); `SoftProofProcessor`
performs real profile round trips through destination and monitor profiles with
selectable rendering intent, and produces separate gamut warnings.

**Export is not.** `ImageExporter` always tags `sRGB IEC61966-2.1` (`:134`) and
rasterizes through the non-wide display context, because `renderFullResolution`
never requests `preserveWideGamut`. Soft-proof settings do not influence exported
files. **Sophisticated on-screen proofing feeding an sRGB-only 8-bit export is
the clearest capability asymmetry in the product.**

### 4.4 Catalog and organization

SQLite (`user_version = 12`), 15 tables. Quick Collection, named collections,
nested collection sets, smart collections, hierarchical keywords, persistent
color-label sets, manual and capture-time-auto photo stacks, missing-file
detection with relink/removal, and catalog-wide duplicate detection using a
**metadata-insensitive decoded-image-data SHA-256** with a whole-file fallback
(`FileContentHasher.swift`).

### 4.5 Metadata and XMP

Read via ImageIO at scan time for every file. XMP sidecars are read on scan when
no stored state exists, and written **only** on explicit user command
(`LibraryViewModel.swift:4198`) — never automatically. Sidecars always target
`basename.xmp`, never the image (`XMPSidecarService.swift:97-99`). An existing
third-party packet is parsed and preserved rather than clobbered.

### 4.6 People — real detection, weak identity

Face detection is real (`VNDetectFaceCaptureQualityRequest`,
`PeopleAnalyzer.swift:383`). **Clustering, however, uses a generic image feature
print of the cropped face region** (`VNGenerateImageFeaturePrintRequest`, `:409`)
rather than Apple's dedicated face-print API. This measures overall appearance
similarity — lighting, pose, background — rather than facial identity, so
suggestions will be materially weaker than a face-print approach.

`README.md` frames this correctly: *"a confirmation-first organizer, not a claim
of biometric identity."* Suggestions always require explicit user confirmation.

### 4.7 Map, culling, review layouts

Map: embedded/manual GPS, direct assignment, GPX track matching, saved radius
locations, and private location-stripping export (MapKit/CoreLocation).
Assisted Culling: on-device focus/eye/exposure/misfire/document scoring with
manual overrides. Review: Compare, Survey, and Reference layout planners.

## 5. Explicit non-goals

Stated in `README.md:1523-1631` and consistent with the code: no tethering, print
or book output, plugins, cloud sync, mobile or web client, collaboration,
panorama/HDR merge, learned RAW denoise or Super Resolution, generative fill,
Copy as DNG, or bundled Adobe camera/lens profile databases.

## 6. Behavior a new engineer must not get wrong

1. **Auto Import permanently deletes from the watched folder.** The code requests
   `mode: .copyToFolder` (`AutoImportService.swift:148`) and then deletes the
   source anyway in its own loop (`:187`), bypassing
   `PhotoImportMode.removesVerifiedSources` entirely. The UI is honest; the code
   is misleading.
2. **No deletion goes to the Trash.** `trashItem` appears nowhere in the
   repository. Every deletion is a permanent `removeItem`.
3. **A "full-resolution" export may not be from RAW.** Silent fallback to the
   embedded ~4096 px JPEG preview is possible and unreported
   (`RAWDOCK_DATA_SAFETY.md` §6.2).
4. **Relink verifies only the file extension** — not size, not content — and
   carries over the *old* file's EXIF (`CatalogStore.swift:2121-2169`).
5. **User state is written to two stores**, and the SQLite write is `try?`
   (`LibraryViewModel.swift:4224`).

## 7. Documentation reliability

The documentation corpus (101 KB README plus seven `Docs/` QA files) is
**unusually accurate** — notably more so than is typical. Claims spot-checked
against code held up, including the non-obvious "SHA-256-keyed thumbnail cache"
(the disk filename really is a SHA-256 digest of the cache key,
`ImageCache.swift:203-206`), "source image files are never rewritten" (confirmed
by exhaustive grep), and the destructive nature of Auto Import.

The `Known gaps versus Lightroom` section (`README.md:1523`) is candid and
appears reliable. **Treat the README as high-quality evidence** — but still
verify the five items in §6, none of which the README frames as sharply as the
code warrants.
